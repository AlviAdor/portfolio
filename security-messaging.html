Security Deep Dive

Locked by design, not by promise.

Text, voice calls, video calls, and file attachments — every one of them encrypted end to end, by default, with no toggle to remember to switch on. Not "encrypted at rest." Not "encrypted on our servers, which we can still read." Encrypted before it leaves your device, decrypted only after it reaches the other person's.

Every channel, locked the same way

Not just messages. Everything.

🔒 Text

RSA-OAEP + AES-256-GCM

Every message is encrypted in your browser with a fresh AES key, which is itself wrapped with the recipient's RSA public key, before any network request is made. The database stores ciphertext — nothing else.

🔒 Voice & video calls

DTLS-SRTP, peer to peer

Once two browsers connect, audio and video flow directly between them — never through this server at all. That's mandatory in the WebRTC spec, true even when a relay server helps two people connect through a restrictive network.

🔒 Call setup itself

The part most apps don't bother with

The offer, answer, and connection candidates that let two browsers find each other are metadata most systems leave in the clear. Here they're encrypted the same way a message is — the server relays ciphertext for that too.

🔒 File attachments

Photos and PDFs, same guarantee

An attached file is encrypted client-side before upload — content and even its filename. The server's database can confirm a file exists; it cannot say what it is, what it's called, or what's inside it.

Why this is worth explaining

"Encrypted" doesn't always mean what it sounds like.

Most people hear "encrypted" and assume it means one specific thing: nobody but the two people talking can read it. In practice, that word covers a wide range of very different guarantees, and the gap between them is exactly where real breaches happen.

A message can be "encrypted" purely in transit (HTTPS) and still sit as plain, readable text on a company's server afterward — encrypted to the server, not past it. Some well-known chat apps are genuinely end-to-end encrypted only in an opt-in mode you have to know to turn on, while the default, everyday conversation stays server-side and readable by the provider. SMS text messages, still how a huge amount of the world communicates, have no encryption of their own at all. And even where message content is properly end-to-end encrypted, the metadata rarely is — who you talk to, when, how often, and from where is often collected and retained regardless, which is frequently the more revealing half of a conversation anyway.

That gap — a product that's secure in its marketing and merely adequate in its architecture — is the thing this project set out to not do. Every piece built here (text, calls, call setup metadata, file attachments) uses the same real guarantee: content is encrypted on your device with a key the server never holds, and the database behind this site — the thing an actual breach would expose — only ever contains ciphertext. I can open phpMyAdmin myself, the person who built this, and read nothing. That's not a policy I'm promising to follow. It's the only thing the code is capable of doing.

Modern Web Developer Standards

CSP Headers

Content Security Policy

Strict CSP headers prevent XSS attacks. External scripts and inline code are blocked by default.

HSTS

Forced HTTPS

HTTP Strict Transport Security header ensures all communication is encrypted. No fallback to HTTP.

CORS

Cross-origin protection

Strict CORS policies prevent unauthorized cross-site requests. Your data stays within trusted boundaries.

SRI

Subresource integrity

Every external resource is verified by cryptographic hash. Tampering is detected immediately.

No Data Stolen. Period.

This isn't just marketing. I use modern cryptography, strategic database isolation, and zero-knowledge architecture because I believe in the principle: your data should not exist in a form I can read. Encryption is not optional—it's the foundation. Every layer is designed so that even if the database is breached, the attacker gets encrypted gibberish. That's modern security. That's what a contemporary web developer practices.
