Why I built it this way

This started as a university Web Technology project, built with a teammate, and I used it to practice something I kept reading about but hadn't actually done: an MVC architecture with real role separation, not just a login check sprinkled on top of a flat script.

Staff accounts are split into roles with genuinely different capabilities -- a doctor can enter diagnoses and update patient records; front-desk staff can register patients and manage appointments; only an admin account can manage other accounts. That separation is enforced in the controller layer on every request, not just by hiding buttons in the view.

The parts I spent the most time on weren't the CRUD screens -- they were the boring-sounding bits: session handling that survives a page refresh without leaking state between roles, a patient/admission/billing schema normalized enough that updating one record can't silently desync another, and consistent server-side validation so a malformed request from curl gets rejected exactly the same way a malformed form submission would.

It's still a student project, not a HIPAA-compliant production system -- but the security habits in it (parameterized queries, role checks on every controller action, session integrity) are the same ones carried through into everything I've built since, including the Secure Auth Demo below.
